## Вывод

**В текущем виде изменения не готовы к слиянию.** Найдены 12 воспроизводимых проблем: 4 с приоритетом P1 и 8 с приоритетом P2. Основные риски связаны с записью неверного прогресса, переходами между заданиями и расхождением контрактов между генераторами, планировщиком и Telegram UI.

Воспроизведения не вызывают LLM и Telegram: заранее заданные результаты semantic grader проверяют поведение приложения после такого вердикта. Это не проверка качества языковых решений настоящей модели.

## P1: исправить перед слиянием

### 1. «Дальше без оценки» записывает ошибку для свободного ответа

Места: [кнопка](../../bot/keyboards.py#L315), [обработчик](../../bot/drill.py#L279), [запись результата](../../vocab/scheduler.py#L1729).

Кнопка получила текст «Дальше без оценки», но продолжает отправлять `GradeCallback(action="wrong")`. `override_answer_incorrect()` делает исход нейтральным только для непроверенных кнопочных заданий. Для обычного `flashcard_ru_de` без подсказки он по-прежнему записывает отрицательный review.

**Воспроизведение:** отправить несовпадающий свободный ответ, завершить проверку ошибкой API, вызвать действие этой кнопки. Получено: `neutral=false`, `assessed=true`, `reviews=[{correct:false, quality:1}]`, `progress.lapses=1`. Для ранее изученного слова этот путь также сбрасывает серию. В сообщении появляется «Ответ засчитан неверным по выбору ученика», хотя ученик выбрал пропуск.

**Исправление:** обе кнопки продолжения после сбоя направлять в один нейтральный `skip_task()`. Убрать дублирование «Дальше» / «Дальше без оценки». Старый callback `wrong` также должен соответствовать обещанию в уже отправленных сообщениях. Проверять реальную цепочку `rendered keyboard → callback → DB` для свободного и кнопочного ответа.

### 2. Старая кнопка «Дальше» аннулирует текущее задание

Места: [разрешение действия для answered](../../bot/drill.py#L430), [безусловная выдача следующего задания](../../bot/drill.py#L384), [возврат старого результата](../../vocab/scheduler.py#L1392).

`skip_task()` возвращает сохранённый результат уже завершённого задания. `skip_current_task()` принимает такой возврат за новое завершение и вызывает `send_task()`. Создание задания затем переводит открытое задание пользователя в `voided`.

Это достижимо обычным нажатием: после текстового ответа бот отправляет отдельный вердикт, а клавиатура под исходным вопросом остаётся. Пользователь может нажать её «Дальше», когда уже показан следующий вопрос. Возможен и повтор одного callback.

**Воспроизведение:** ответить на A, получить B, вызвать старый skip для A. B становится `voided`, появляется C. Ответ на B после этого не принимается.

**Исправление:** возвращать признак фактически выполненного перехода и выдавать следующее задание только его победителю. Проверку текущей сессии/задания и создание следующего задания выполнять атомарно. Повторный callback должен вернуть тот же результат или ничего не делать. Удаление старой клавиатуры полезно для UI, но не заменяет защиту в backend.

### 3. После подсказки слово немедленно повторяется и получает ложный самостоятельный зачёт

Места: [исключение карточки из сессии](../../vocab/scheduler.py#L795), [поиск предыдущего раскрытия](../../vocab/scheduler.py#L858), [подсказка](../../vocab/scheduler.py#L1755), [рендер задания](../../bot/presentation.py#L55).

При правильном ответе после подсказки выставляется нейтральный исход, но `neutral_blocks_session` остаётся false: условие не включает `assistance_level > 0`, если `target_reproduced=true`. Срок повторения остаётся просроченным, поэтому обычный планировщик снова выбирает ту же карточку. Проверка предыдущего раскрытия также не учитывает ответ после подсказки. Если снова нажимать подсказку, карточка может повторяться без конца; если просто повторить только что увиденный ответ, SRS считает его самостоятельным.

**Воспроизведение:** карточка `schnell`, просроченный интервал 21 день; подсказка → правильный ответ → автоматическая выдача следующего задания. Получено то же слово с тем же вопросом. Второй ответ получил `neutral=false`, интервал вырос до **54,6 дня**.

Дополнительная несогласованность: `task_text()` уже показывает `payload.hint`, а `record_hint()` повторно выдаёт ровно этот текст и нейтрализует попытку. Для `schnell` и до, и после нажатия виден перевод «быстро». Подготовленные `teaching_metadata.hints` при этом не переносятся генераторами в поля, которые читает `record_hint()`: обещанная цепочка из нескольких подсказок в обычных заданиях не подключена.

**Исправление:** разделить постоянную смысловую опору и дополнительные подсказки; сохранять дополнительные подсказки в снимок задания. После учебной попытки исключать карточку из обычной очереди этой сессии. Если предлагается отдельная повторная попытка, она должна оставаться учебной независимо от нового task ID.

### 4. Материал с собственной версией навсегда застревает на знакомстве

Места: [версия для поиска истории](../../vocab/scheduler.py#L179), [версия создаваемого introduction](../../vocab/exercises/fair.py#L71). Та же константа используется остальными подготовленными генераторами.

Планировщик ищет просмотр материала по `metadata.review.version`, но генераторы записывают глобальный `fair-synonym-pilot-v1`. Эти значения совпадают только у встроенного пилота. Свою версию можно задать через предусмотренные моделью карточки метаданные.

**Воспроизведение:** взять корректный пилотный материал и изменить только `review.version` на `custom-v2`. Три последовательные обычные сессии дают `introduction → introduction → introduction`. Все задачи сохраняют `fair-synonym-pilot-v1`. После каждого знакомства карточка исключается до следующей сессии; до обычного повторения дело не доходит.

**Исправление:** брать версию из конкретного валидированного материала во всех генераторах и проверках истории. Версию схемы и версию содержимого хранить отдельно. Добавить проверку с двумя пользовательскими версиями, а не только с глобальной константой.

## P2: функциональные ошибки

### 5. Новый валидатор отключает упражнения на управление глаголов

Места: [валидатор](../../vocab/scheduler.py#L398), [существующий контракт rection](../../vocab/exercises/grammar.py#L130).

Валидатор требует `accepted ⊆ options` для любого кнопочного задания. У `grammar/rection` поле `accepted` содержит нормальные текстовые написания одного ответа: `auf Akk`, `auf + Akk`, `auf Akkusativ`, `warten auf Akk` и т.д. Кнопка содержит только `auf Akk`. Поэтому проверка всегда отвергает такой результат.

**Воспроизведение:** для `warten auf Akk` низкоуровневый генератор возвращает упражнение; `_validate_generated_task()` возвращает false; `create_task(task_type="grammar")` возвращает `None`. Число отвлекающих вариантов не устраняет причину. При автоматическом подборе этот тип может молча заменяться fallback-упражнением.

**Исправление:** разделить допустимые кнопки и текстовые алиасы ответа. Валидировать идентификаторы правильных вариантов относительно кнопок, а алиасы — по отдельному контракту. Проверять выход каждого настоящего генератора через общий валидатор.

### 6. Принятый ответ ученика теряется по дороге в Telegram

Места: [возвращаемый результат](../../vocab/scheduler.py#L1016), [ожидания рендера](../../bot/presentation.py#L94).

`_commit_review()` сохраняет `answer` в JSON вердикта в БД, но не включает его в возвращаемый словарь `result`. Именно этот словарь сразу получает `verdict_text()`. Поэтому ветки «Ваш ответ» и «Ещё один вариант» в реальном потоке не работают. Тест рендера подставляет `answer` вручную и не обнаруживает разрыв.

**Воспроизведение:** в пропуске для `zugänglich` принять `geöffnet` с `target_reproduced=false`. Возвращаемый результат не содержит `answer`; рендер показывает «✅ Подходит», затем **«Ответ: zugänglich»**. Принятое `geöffnet` отсутствует.

**Исправление:** единый тип результата для сохранения и возврата, с обязательным `learner_answer`. Рендерить реальный результат backend в интеграционном тесте принятой альтернативы.

### 7. Ограничение «одна дополнительная попытка на слово» обходится цепочкой потомков

Места: [условие показа retry](../../vocab/scheduler.py#L788), [поиск существующего retry](../../vocab/scheduler.py#L1563).

Поиск ограничен `retry_parent_task_id`. Если пользователь в дополнительной попытке снова передал смысл без обязательного слова, этот дочерний task получает `retry_available=true` и может создать собственного потомка. Проверяется один ребёнок на родителя, а требовалась одна дополнительная попытка на слово в сессии.

**Воспроизведение:** в длинной сессии трижды ответить `Das Produkt ist wieder auf Lager.` на требование использовать `verfügbar`, каждый раз принять смысл и отметить отсутствие цели. Создаются три разных retry, все без ошибки.

**Исправление:** ограничение на `(session_id, word_id)` с признаком использования дополнительной попытки. Для retry-задачи не предлагать ещё один retry. Проверять не только два параллельных вызова для одного родителя, но и цепочку `parent → child → grandchild`.

### 8. У обычных фраз показывается неработающая кнопка повторной попытки

Места: [генерация повторной попытки](../../vocab/scheduler.py#L1620), [ограничение генератора](../../vocab/exercises/fair.py#L96), [удаление кнопок при ошибке](../../bot/drill.py#L492).

`phrase_context` теперь имеет цель `target_usage`. Его вердикт может предложить retry. Но `start_target_retry()` пытается построить его только через `fair.TargetUsage`, который требует reviewed teaching metadata. Обычные фразы такими материалами не обладают. Fallback разрешён только после раскрытия открытого задания, а здесь исходная задача уже отвечена.

**Воспроизведение:** `auf jeden Fall` без метаданных → `phrase_context` → принять `Ich komme bestimmt.` как передачу смысла без цели. Получено `retry_available=true`, затем `retry unavailable` при нажатии. Обработчик убирает всю клавиатуру, включая «Дальше», хотя автоматический переход ранее был приостановлен.

**Исправление:** строить повтор по снимку и типу исходного задания; `phrase_context` не должен зависеть от пилотного словаря. Доступность действия должна вычисляться по тем же условиям, по которым оно выполняется. При неудаче сохранять возможность продолжить.

### 9. Некорректные teaching metadata проходят валидацию и ломают генерацию

Места: [WordCard](../../vocab/words.py#L65), [validated_metadata](../../vocab/teaching.py#L275), [потребитель](../../vocab/exercises/cloze.py#L144).

`validated_metadata()` возвращает любой непустой dict. `WordCard` проверяет только номер схемы и статус review. Формы вложенных `examples`, `recall_alternatives`, `contrasts`, ограничения вариантов и обязательные поля не проверяются. CSV-импорт дополнительно идёт через `Word`/`validate_word`, где новой структурной проверки вовсе нет.

**Воспроизведение:** `teaching_metadata={schema_version:1, review:{status:"draft"}, recall_alternatives:["invalid entry"]}` успешно проходит `WordCard` и сохраняется. Создание cloze падает с `AttributeError: 'str' object has no attribute 'get'`.

**Исправление:** общая типизированная модель материала для агента, импорта, исправления карточек и генераторов. Невалидные дополнительные материалы не должны обрушивать тренировку карточки. Draft-материалы не должны автоматически давать проверенные допустимые ответы. Название `validated_metadata` должно соответствовать выполняемой проверке.

### 10. Подготовленные альтернативы для zugänglich никогда не подключаются

Места: [сопоставление контекста](../../vocab/exercises/cloze.py#L129), [материал пилота](../../vocab/teaching.py#L92).

В metadata записан шаблон `Der Garten ist für Besucher ____.`. Генератор делает пропуск длиной в слово: `Der Garten ist für Besucher __________.`. Сравнение строк точное, поэтому ни `geöffnet`, ни `offen` не попадают в `accepted_neutral`.

**Воспроизведение:** создать штатный cloze для пилотной карточки и ответить `geöffnet`. Вместо локального принятия получается pending LLM evaluation; `accepted_neutral` отсутствует. При недоступном grader уже проверенный ответ нельзя автоматически зачесть.

**Исправление:** стабильный идентификатор контекста или единый placeholder в шаблоне; длину подчёркивания применять только при отображении. Тест должен создавать упражнение из реального встроенного материала без ручного изменения `expected`.

### 11. Миграция оставляет старые открытые задания с небезопасной проверкой

Места: [миграция 015](../../vocab/migrations/015_fair_synonym_practice.sql#L1), [выбор пути проверки](../../vocab/scheduler.py#L1126).

Добавление `objective DEFAULT 'recall'` не обновляет контракт ранее выданных заданий. Старый `choice_ru_de` сохраняет `grading_policy='deterministic'` и единственный эталон; миграция не завершает такую задачу нейтрально и не переводит её на новый безопасный путь. После обновления бот может принять ответ на уже отправленное сообщение.

**Воспроизведение:** в заполненной схеме v14 создать открытый выбор между `zugänglich` и `verfügbar` для подсказки «доступный», применить v15, выбрать второй вариант. Получено `pending=false`, `correct=false`, `neutral=false`, `grading_source='deterministic'`. Ошибка ученика записывается без semantic grader.

**Исправление:** явная политика перехода для старых открытых tasks и pending evaluations: безопасная адаптация поддерживаемого снимка либо завершение/аннулирование без изменения SRS с понятным продолжением для пользователя. Закрытую историю переоценивать не требуется.

### 12. После миграции статистика сессий получает неверный знаменатель

Место: [assessed_count в миграции](../../vocab/migrations/015_fair_synonym_practice.sql#L42).

Для существующих сессий новое поле получает ноль, хотя `answered_count` и `correct_count` уже заполнены. Рендер теперь использует именно `assessed_count`, поэтому история и открытые сессии становятся несогласованными.

**Воспроизведение:** перед миграцией 5 ответов, из них 4 правильных. После миграции: «5 завершено, оценённых ответов нет». После одного неправильного и одного правильного ответа: **«5/2 правильных (7 завершено)»**.

**Исправление:** заполнить новый счётчик по прежней семантике существующих сессий, затем использовать новые правила для новых исходов. Добавить проверку `correct_count <= assessed_count <= answered_count`, учитывая совместимость со старой схемой.

## Что стоит изменить в устройстве решения

### Единый контракт результата и одно место принятия решения о SRS

Сейчас одно состояние одновременно описывается `correct`, `conditions_met`, `target_reproduced`, `defect_type`, `srs_action`, `assessed`, `neutral_reason`, `retry_available` и дополнительными признаками. Условия нейтральности повторяются в `begin_answer_submission()`, `finalize_tutor_evaluation()` и `_verdict_policy()`. Сохранённый и возвращаемый вердикты собираются отдельно. Именно здесь уже разошлись поля ответа и правила помощи.

Предлагаю ввести типизированный результат проверки с тремя явными частями:

- Выполнено ли видимое задание и какая нужна обратная связь.
- Есть ли свидетельство самостоятельного воспроизведения конкретной цели.
- Какое действие над расписанием, счётчиками и продолжением сессии следует из этих фактов.

Локальный checker и LLM должны заполнять одну структуру языковой проверки; код один раз вычисляет последствия и один раз сериализует результат. Нельзя делегировать модели вычисление интервала или разрешение retry.

### Разделить переход по сессии и завершение отдельного ответа

Полезна единая операция вроде `advance_session(expected_task_id, action)`, которая под блокировкой проверяет актуальный task, фиксирует переход и возвращает следующий доступный task. Telegram-обработчик только отображает результат.

Ограничения помощи и дополнительной попытки относятся к слову внутри сессии. Их следует хранить/вычислять по `(session_id, word_id)`, а не по цепочкам task ID. Это одновременно закрывает повторные callback, потерю текущей карточки и бесконечные retry.

### Упростить пользовательский сценарий знакомства

Даже у встроенного материала с правильной версией `introduction` блокирует слово до следующей сессии; `target_usage` делает то же самое. При обычном автоматическом выборе первое SRS-повторение нового пилотного слова оказывается доступно лишь в третьей сессии. Тест холодного старта обходит это, явно передавая `word_id` при выдаче следующего упражнения.

Стоит разрешить понятный учебный переход «знакомство → одна практика с показанным словом» внутри той же сессии. Он остаётся нейтральным для SRS и укладывается в бюджет короткой сессии. После этого слово исключается из обычной очереди до независимого повторения. Текущий запрет слишком грубый для обучения и одновременно недостаточен для подсказок.

### Видимые условия должны действительно быть видимыми

В [flashcard.RuDe](../../vocab/exercises/flashcard.py#L97) записано `visible_constraints={"target": visible_word}`, хотя текст вопроса показывает только перевод. Grader получает указание использовать visible_constraints как контракт. Это оставляет структурное противоречие в самой функции, которую изменения должны сделать справедливой.

Скрытую целевую карточку следует хранить отдельно от видимых требований. В `visible_constraints` нужны только фактически отображаемые условия, например обязательный артикль. Наличие слова в серверном словаре не делает его условием вопроса. Для `free_expression` и `target_usage` стоит использовать разные типы задания с различимыми обязательными полями.

Это подтверждённое противоречие данных; конкретную частоту ложных решений настоящей LLM в этом ревью не измерял.

### Учебный материал должен быть данными с общей схемой

Сейчас словарные материалы, версии, автоматическое подключение по точному примеру и правила проверки тесно связаны. У агента есть подробные модели, у domain-слоя — `dict[str, Any]`, а генераторы самостоятельно читают вложенные ключи.

Нужна одна модель `TeachingMetadata`: отдельные версии схемы и материала, обязательные поля reviewed-материала, связанные значения и типизированные контексты. Назначение статуса `reviewed` агентом само по себе не подтверждает языковую корректность. Правила доступа к проверенным альтернативам должны быть едиными для contrast, cloze и объяснения различий.

### Сократить количество действий и технических пояснений в Telegram

- Одна кнопка «Дальше» с единым поведением.
- «В чём разница?» показывать при наличии подходящего сравнения; сейчас она добавляется к любому ответу.
- При принятом синониме сначала показывать ответ ученика, затем пример с изучаемым словом.
- Вместо «не засчитано в SRS» достаточно «Это слово повторим отдельно».
- Различать «попробовать применить слово» и механическое «набрать показанный ответ ещё раз»: сейчас fallback после раскрытия делает именно второе.

## Почему тесты прошли

Покрытие полезно для блокировок, повторной финализации и отдельных генераторов, но многие новые проверки перескакивают через место интеграции:

- Рендер проверяется на вручную собранном словаре с `answer`, которого нет в реальном результате.
- Retry проверяется двумя вызовами одного родителя и успешным ответом ребёнка; повторная ошибка ребёнка не проверяется.
- Контрастный тест после генерации вручную заменяет `expected.accepted`.
- Проверка грамматики через общий scheduler не покрывает `grammar/rection`.
- Новая миграция проверяется на применимость, но не на продолжение уже заполненной сессии и старого открытого задания.
- Холодный старт часто задаёт `word_id` явно и тем самым обходит реальную фильтрацию очереди.

Следующий набор регрессионных тестов должен проходить реальные цепочки `генератор → снимок → проверка → результат → UI` и `callback → переход сессии → БД`. Для семантики нужен отдельный небольшой набор настоящих проверок grader; моки этой задачи не решают.

## Предлагаемый порядок работы

1. Исправить ошибочный отрицательный skip, старые callback и учёт помощи. Это напрямую влияет на пользовательские ответы и прогресс.
2. Согласовать версии материала, контракт кнопочных вариантов и возвращаемый результат.
3. Исправить оба сценария retry и переход от знакомства к учебной практике.
4. Ввести общую валидацию метаданных, стабильные шаблоны пропусков и заполнение новых полей при миграции.
5. Проверить реальные интеграционные цепочки, затем пройти сценарии в Telegram и отдельно оценить semantic grader.
